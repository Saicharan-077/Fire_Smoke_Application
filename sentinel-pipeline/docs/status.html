The approach

Implementation strategy

Separate service built alongside the running app, with a committed deletion step. The phases below are a real sequence — each depends on the one before it.

P1

Build the pipeline standalone Done

New service at sentinel-pipeline/: own process on port 8100, own SQLite database, own evidence store, one versioned /v1 API. The existing app keeps running, untouched. Chosen over in-place extraction because the old code has no seam — detection logic is interleaved with auth, DB writes, and WebSocket broadcast inside route handlers.

P2

Dashboard consumes the API Deferred

Detection, Live Monitoring and Alerts pages repoint at /v1. Alert lifecycle — PIN resolution, escalation, operator notes — stays entirely dashboard-side, keyed by the alert IDs the pipeline issues. Proposal only; not executed, by instruction.

P3

Delete the superseded paths Deferred

The eight motion filters and the embedded RTSP pipeline get removed, not merely bypassed. Cutover is not complete until this runs — otherwise the duplicate-implementation pattern this rebuild exists to end simply persists in a new form.

Principles held throughout

Carry over, don't rewrite. The model loader, the Tier-1 HSV/texture rules, and the ByteTracker were moved and extended rather than reimplemented — the originals are superseded, not duplicated.

One decision point per concern. Exactly one place decides to skip a frame (the Gate), one place runs the model, one place creates alerts. Each is enforced structurally, not by convention.

The pipeline owns its data. No reads or writes against the dashboard's tables. Config is resolved once at import, never from a database on a hot path.

Classifier as an in-process plugin. Numpy arrays pass by reference with no serialisation. The stub and the real classifier are drop-in interchangeable.

Nothing is “done” on code review. Every completion claim below has a live test with real output behind it.

Errors found in my own work

Recorded because the corrections matter more than the claims did.

Tracker silently dropped candidates

Textbook ByteTrack opens new tracks only from high-confidence detections. Against a 0.20 recall floor that discarded every 0.20–0.35 candidate not already tracked — reinstating a recall filter upstream of the Classifier, the exact anti-pattern this rebuild removes. Now 17/17 reach it.

Benchmarked the test harness, not the Gate

9.9 ms of the measured 10.9 ms was numpy noise generation inside the timing loop. True Gate cost is 0.74 ms.

Illumination assertion was wrong in direction

I expected possible suppression of fire; at ≥10% frame coverage normalisation amplifies. The assertion was replaced with the detection-relevant invariant: no fire crosses from above threshold to below.

Overstated the forced-override tier coverage

The original 9/9 used a single hardcoded override throughout; only the mapping function covered all four tiers. Closed with a dedicated 6/6 suite.

Recommendation

Suggested next step

T1 and T2 unblock the most. T1 lets the Classifier team finalise Phase 4; T2 decides whether any model retraining is needed at all, and costs one command.

On the pipeline side, persistence (T10 + T11) is the most valuable unblocked work. Zones and calibration currently live in memory, so a restart loses an approved zone — which matters the moment this runs anywhere real.

T14 should be settled before T7, not after. The API is unauthenticated; that is fine on localhost and not fine once the Dashboard talks to it across a network.
